# 03 · 数据准备与分块

原始金融文档是 PDF / TXT / HTML 混合格式，不能直接喂给检索系统。本项目的预处理管线把它们变成**结构化的分块（chunk）**：先解析出文本与层级，再按标题栈、表格、Token 预算切出可检索的最小单元。

## 3.1 流水线总览

```text
data/raw/raw/<领域>/                原始文件（PDF / TXT / HTML）
        │
        ├── mineru.py ─────────────────────► data/processed_md/*.md
        │     (MinerU API：PDF 识别、表格、公式 → Markdown)
        │
        ├── document_parser.py ───────────► data/processed/*.json
        │     (pdfplumber：章节树 + 平坦段落)
        │
        └── chunker_md.py ────────────────► data/chunks/<领域>/*.json
              (Markdown/TXT → 语义分块，核心引擎)
                    │
                    ├── chunker_lc.py（可选 LangChain 方案 → data/chunks_lc/）
                    │
                    └── scripts/split_chunks.py（可选二次切分）
                                │
                                ▼
                    data/chunks/all_chunks.json  ← BM25 建索引的输入
```

## 3.2 原始数据目录结构

```text
data/raw/raw/
├── insurance/              # 保险条款（PDF）
├── regulatory/
│   ├── html/               # 监管法规 HTML
│   ├── attachments/        # 附件 PDF
│   └── txt/                # 清洗后的 TXT（如 strict_v3_*.txt）
├── financial_contracts/    # 金融合同（PDF）
├── financial_reports/      # 上市公司年报（PDF）
└── research/               # 行业研报（PDF）
```

> 官方数据请从赛题页面下载后放入 `data/raw/raw/`。

## 3.3 两条解析路径

### MinerU：PDF → Markdown（图文混排文档）

`data_processing/mineru.py` 调用 MinerU 在线服务，把 PDF 转成 Markdown，能较好地保留表格与公式结构。管线分五步：

1. `_walk_raw_dir` / `collect_files`：递归收集原始文件，构建文档清单；
2. `_split_pdf`：超过 200 页的大 PDF 先按页切分到 `data/temp/`；
3. `upload_batch`：批量上传（`model_version="vlm"`）；
4. `poll_results`：轮询下载结果到 `data/processed_md/`；
5. `_merge_chunks` / `_cleanup_temp`：合并分块文件并清理临时目录。

```bash
python -m data_processing.mineru check       # 校验文档映射
python -m data_processing.mineru --dry-run   # 只扫描不处理
python -m data_processing.mineru --limit 3   # 试跑前 3 个
python -m data_processing.mineru --force     # 强制重新处理
```

### document_parser：PDF / TXT / HTML → 章节树（本地解析）

`data_processing/document_parser.py` 基于 pdfplumber，提供两套标题识别策略：

- **rich 策略**（`process_docs` 演进）：按词分组 + 字号判断标题层级，适合 PDF；
- **simple 策略**（`document_processor` 演进）：逐行正则匹配标题，适合 TXT/HTML。

核心结构是 `Section` 树：`level / title / content / children`，可输出两种形态：

- `to_dict()`：嵌套树形 JSON；
- `to_flat()`：展平为 `header_path`（如 `第一章 > 第一节 > 第一条`）加正文的列表。

标题匹配规则（`PATTERNS`）覆盖 `1.`、`1.1.`、`1.1.1.`、`第X章`、`第X条`、`第X类`、`一、`、`（一）` 等常见写法；同时有两类反向规则：

- `LIST_PATTERNS`：`（1）`、`a.`、`①`、`1、` 等**列表项**不算标题；
- `HEADER_FILTER_PATTERNS`：页码、"请扫描以查询验证条款"等**页眉页脚**直接过滤。

```bash
python -m data_processing.document_parser        # 处理全部
python -m data_processing.document_parser check  # 校验文档映射
python -m data_processing.document_parser qa     # 查看题目-文档覆盖
```

## 3.4 Token 估算口径

所有分块与预算控制统一使用 `_utils.tok()`：

```text
tok(text) = CJK 字符数 / 1.8 + 其他字符数 / 4 + 1
```

即一个汉字约 0.56 token，一个英文/数字字符约 0.25 token。它不是精确计数，但足够在**离线阶段**统一估算 chunk 大小、控制上下文预算，与线上计费口径的偏差在检索阶段可接受。

## 3.5 分块引擎（chunker_md，核心）

`data_processing/chunker_md.py` 是预处理的关键，参数为：

```text
TARGET = 350   # 目标块大小（token）
MIN_T  = 100   # 低于此值的短块向前合并
MAX_T  = 400   # 单块硬上限（超过先拆再打包）
```

完整流程：**标题约定检测 → 标题分类 → 层级栈建 header_path → 同级合并 → 正文切分打包 → 空块清洗**。

### 3.5.1 标题约定自动检测

不同文档的编号体系不同：金融合同/年报常用"第X节 → 一、 → （一）"（中文在上），保险条款/部分研报常用"1. → 1.1. → 一、"（阿拉伯在上）。程序扫描全文标题自动判断：

1. 只要出现 `第X章 / 第X节` → 强制约定 A；
2. 否则看前 3 个编号标题：全是阿拉伯编号且没出现中文编号 → 约定 B；
3. 其余情况 → 约定 A。

#### 约定 A（中文在上）：金融合同 / 年报 / 监管

| 模式 | rank | 类型 |
|------|------|------|
| `第X章` | 1 | T_CHINESE |
| `第X节` | 2 | T_CHINESE |
| `第X条` | 3 | T_CHINESE |
| `一、` / `一．` / `一.` / `一）` / `一)` | 4 | T_CHINESE |
| `（一）` | 5 | T_CHINESE |
| `1.` / `1、` / `1．` | 6 | T_ARABIC |
| `1.1.` / `1）` / `1)` / `（1）` / `(1)` | 7 | T_ARABIC |
| `1.1.1.` | 8 | T_ARABIC |
| `1.1.1.1.` | 9 | T_ARABIC |
| 其他 | None | T_PLAIN |

#### 约定 B（阿拉伯在上）：保险条款 / CMB 年报 / 部分研报

| 模式 | rank | 类型 |
|------|------|------|
| `第X章` | 1 | T_CHINESE |
| `第X节` | 2 | T_CHINESE |
| `第X条` | 3 | T_CHINESE |
| `1.` | 4 | T_ARABIC |
| `1.1.` | 5 | T_ARABIC |
| `1.1.1.` | 6 | T_ARABIC |
| `1.1.1.1.` | 7 | T_ARABIC |
| `1、` / `1．` | 8 | T_ARABIC |
| `1）` / `1)` | 9 | T_ARABIC |
| `一、` / `一．` / `一.` / `一）` / `一)` | 10 | T_CHINESE |
| `（一）` | 11 | T_CHINESE |
| `（1）` / `(1)` | 12 | T_CHINESE |
| 其他 | None | T_PLAIN |

> rank 越大层级越深；同一条规则中多段式编号（`1.1.1.`）必须排在单段式（`1.`）之前匹配，保证 rank 正确。

### 3.5.2 弱标题

标题（去空格后）命中以下关键词之一，标记为 `is_weak=True`：

```text
目录 | 释义 | 备查文件 | 附件 | 摘要 | 声明
TOC | abstract | summary | disclaimer | declaration | glossary | appendix
```

弱标题行为特殊：

- `header_path` 直接写自己的标题，不拼接栈路径；
- 入栈时不与相邻 PLAIN 合并；
- 不参与任何同级/PLAIN 合并；
- 标题只存在于 hp 中，不重复写进正文。

这样"目录""附件声明"这类弱结构不会污染检索路径，也不会把无关章节并进来。

### 3.5.3 层级栈 → header_path

扫描所有 `#1~#6` 标题行，维护一个 `(title, rank, is_weak)` 栈，为每个小节生成 `header_path`：

- **PLAIN（rank=None，非弱）**：追加到栈顶；若栈顶也是非弱 PLAIN 则合并为"前 + 后"。栈全为 PLAIN 时：单个 PLAIN 用自己的标题作 hp；多个连续 PLAIN 的 hp 为空（标题保留在正文首行，避免信息丢失）。
- **弱标题**：直接入栈，hp 等于自身标题。
- **编号标题**：先弹出栈顶所有 PLAIN，再弹出所有 `rank >= 当前 rank` 的编号标题，然后入栈；hp = 栈中编号标题用 ` > ` 连接。

示例：

```text
第一节 保险责任(rank=2) → 一、身故保险金(rank=4) → （一）给付条件(rank=5)
hp = "第一节 保险责任 > 一、身故保险金 > （一）给付条件"
```

### 3.5.4 同级合并（迭代至收敛）

相邻且满足全部条件的编号小节会合并，减少碎片：

1. 双方非弱标题；
2. 同 rank；
3. 父路径相同（`_parent(hp)` 一致）；
4. 序号连续（`b.seq == a.last_seq + 1`，阿拉伯取最后一段数字，中文经 `_cn2int` 转数字）；
5. 合并后 token ≤ MAX_T(400)。

合并行为：

- 文本合并进第一个 chunk；
- labels 拼接（如 `1.1 + 1.2 + 1.3`），hp 末级同步更新；
- **全覆盖提升**：合并后若父路径下不再有同 rank 的其他小节，hp 提升为父路径，rank/type/seq 更新为父层，继续参与下一轮合并——实现自底向上逐层收敛。

示例：

```text
（一）+（二）+（三）+（四）+（五） → 全覆盖 → hp = "一、与本期债券相关的投资风险"
一、+ 二、 → 全覆盖 → hp = "第一节 风险提示及说明"
```

### 3.5.5 PLAIN 合并

同级合并完成后，相邻的非弱 PLAIN 小节若合并后 ≤ MAX_T 也会合并（hp 置空）；若第一个小节的标题原本只在 hp 中，合并时把标题补回正文首行。

### 3.5.6 正文处理

#### 图片

`![](...)` 从正文提取到 `images` 字段，**不计入 token**，同一小节的所有 chunk 共享一份。

#### 表格（重点）

表格是金融文档里信息密度最高、也最容易拆坏的部分，处理规则：

1. **HTML 表格 → Markdown**：`<table>` 转成 `|...|` 管道表，`colspan` 展开补齐列；
2. **原子段落**：表格作为一个整体参与切分，不跨 chunk 拆分（`_table_aware_split` 先把表格替换成占位符，切段后再还原）；
3. **超长表格按行拆**：超过 MAX_T 时只在行边界拆，每个分片保留表头行（`_split_table_rows`）；
4. **宽表按列组拆**：行拆后仍超限时，以第一列为锚点，按 4/3/2/1 列分组，再在组内按行分批（`_split_wide_table`）；
5. **极端情况截断**：单元格超长时保留前 200 字符加 `...` 兜底（`_truncate_cells`）。

#### 段落切分与打包

```text
按空行拆段（_table_aware_split）
   │
   ├── 段落 > MAX_T 且是表格 → 按行拆
   ├── 段落 > MAX_T 且是普通文本 → 按句号/分号切句，无句号按字符硬切（_split_long）
   └── 段落 ≤ MAX_T → 直接进入打包
           │
           ▼
      贪心打包（_pack）：依次装入，超 MAX_T 换新块
           │
           ▼
      小节内短块合并：tokens < MIN_T(100) 且与上一块合并 ≤ MAX_T → 合并
```

### 3.5.7 空 chunk 清洗

`_is_empty_chunk` 过滤无意义块，但**绝不删除含表格或图片的块**：

- 清除样板文本后剩余 < 10 字符（`无。`、`不适用`、`□不适用` 等占位内容）；
- 目录式块：含 ≥ 2 处 `.. 页码` 引用。

### 3.5.8 TXT 按"第X条"分块

监管法规 TXT（`data/raw/raw/regulatory/txt/`）走独立的 `chunk_txt_articles`：以 `第X条` 为切分点，一条一单元；超长条文再按段落/句子拆后打包，`header_path` 即条文标题。

### 3.5.9 输出格式

```json
{
  "chunk_id": "insurance_1_17",
  "doc_id": "insurance_1",
  "header_path": "第一章 保险责任 > 一、身故保险金",
  "text": "……原文……",
  "tokens": 312
}
```

- `chunk_id` = `{doc_id}_{序号}`（`_number` 按序编号）；
- 有附加数据时带 `images` 字段；
- 每领域输出到 `data/chunks/<领域>/<doc>.json`，最后汇总 `data/chunks/all_chunks.json` 供建索引。

## 3.6 二次切分（split_chunks.py）

`scripts/split_chunks.py` 对 >350 token 的块做二次切分，目标 200-400 token：

```text
切分边界优先级：段落(\n\n) → 句号(。！？) → 分号(；) → 逗号(，) → 硬截断
相邻子块保留约 70 字符（≈40 token）重叠，避免切点切断语义
表格（含 >5 个 |）与 <100 字符的短文本不拆
```

```bash
python scripts/split_chunks.py            # 预览模式（不改文件）
python scripts/split_chunks.py --apply    # 执行并重建 all_chunks.json
```

## 3.7 LangChain 备选方案（chunker_lc）

`data_processing/chunker_lc.py` 是另一套分块实现，供对照实验：

1. 复用 `_match` 的 rank 栈把平级 `##` 归一化为真实多级标题（`_normalize`）；
2. 交给 `MarkdownHeaderTextSplitter` 按标题切分；
3. `_post_chunk` 做表格感知的二次切分与 token 打包（512/80/1024）。

最终提交使用 `chunker_md`：对"第X条/一、（一）"这类中文编号体系，自研层级栈比通用 splitter 更可控。

```bash
python scripts/export_fulltext.py --domains insurance
```

## 3.9 已知局限

- 同一文档内相同 pattern 出现在不同层级（如保险条款中 `1.` 既是顶层又是子要点）时，固定 rank 无法区分，按顶层处理；
- 中文数字转换 `_cn2int` 对"二十"这类写法支持有限（可能返回 2 而非 20），影响序号连续性判断；
- 约定检测只看前 3 个编号标题，边缘 case 可能误判。
